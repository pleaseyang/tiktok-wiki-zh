# 速率限制

# 概述
TTS 开放平台使用动态 QPS 分配机制。您的有效请求容量由多个因素计算得出，包括授权店铺规模、API 资源特性、端点负载和平台级保护规则。
关键原则：

* 平台不为所有端点暴露单一的固定 QPS 查询 API。
* 端点参考文档如果发布了特定的限制或计数规则，则以该文档为准，优先于本页。
* 构建自适应客户端，对限流信号做出响应，平滑请求突发，使用批量 API，缓存热数据，并使用指数退避加抖动进行重试。
* 限流响应并不总是意味着您的应用单独超出了其应用-店铺配额。它也可能是由端点级或平台级的保护性限流引起的。

# 1. 为什么存在 API 速率限制
API 速率限制是保持平台稳定和公平的基础机制。它有两个目标：

* **平台稳定性**：防止流量高峰过载服务并降低所有人的访问质量。
* **公平资源分配**：在开发者之间公平分配平台容量，防止少数应用垄断资源而损害其他应用。

我们强烈建议所有开发者采用行业标准的限流、缓存、批处理和重试模式来构建弹性应用。
# 2. 动态 QPS 分配
## 2.1 配额如何计算
平台不使用统一固定配额，而是动态计算有效请求容量。
| **维度** | **如何影响容量** |
| --- | --- |
| **应用授权规模**（授权店铺数量） | 授权店铺数量是总容量的主要输入。通常，授权店铺越多，总容量越大，但关系不一定是严格线性的。可能是阶梯式的、按端点加权的，并受平台条件调整。授权变更也可能需要时间才能在所有限流系统中生效。 |
| **API 资源特性**（按端点分级） | 轻量级读取 API 通常比重度读取、写入或复杂分析 API 有更高的容忍度。如果端点参考文档指定了不同的限制、计数规则或重试行为，则以该文档为准。 |
| **实时平台负载** | 端点的上限可以根据服务健康状况、流量高峰或保护性控制动态调整。 |
## 2.2 容量规划基线
由于平台配额是动态的且按端点而异，以下值 **不是保证的平台限制**。仅在端点参考文档未发布明确值时，将它们用作客户端限流、容量估算和负载测试基线的保守起点。
| **API 类型** | **每个 App ID x 授权店铺的建议初始发送目标** | **如何使用** |
| --- | --- | --- |
| 重度写入 API 或复杂分析 | 0.2-1 请求/秒 | 从低开始，排队请求，仅在没有限流的情况下持续成功后再逐步增加。 |
| 标准写入 API | 1-3 请求/秒 | 在启用重试之前使用幂等键或等效保护措施。 |
| 标准读取或同步 API | 3-10 请求/秒 | 优先使用增量同步，避免全量拉取。 |
| 轻量级读取或批量 API | 5-20 请求/秒 | 尽可能批处理，并在逐步增加期间监控 429 / `36009002` 速率。 |
建议的逐步增加模式：

1. 从相关范围的低端开始。
2. 逐步增加流量，例如每 10-15 分钟增加 20-30%。
3. 当限流、延迟尖峰或错误率增加时，立即停止增加。
4. 将观察到的稳定速率视为运营基线，而非保证配额。

## 2.3 店铺规模如何影响容量
扩展店铺授权规模是增加总容量最直接的方式，但不要假设精确的线性扩展。

* 随着更多店铺授权同一应用，总容量通常会增加。
* 容量仍受端点分级、平台负载和保护性控制的影响。
* 新授权的店铺可能不会在每个内部限流层中立即提高有效容量。
* 对于大型促销活动、迁移流量高峰或流量峰值，请通过逐步增加测试验证容量。

# 3. 速率限制隔离和触发维度
最小店铺范围隔离单元是 **App ID x 授权店铺** 组合。
| **维度** | **适用时机** | **含义** | **开发者操作** |
| --- | --- | --- | --- |
| App ID x 授权店铺 | 使用有效店铺授权调用的店铺范围端点 | 同一店铺授权给不同应用具有独立的应用-店铺容量。同一应用授权给多个店铺具有独立的店铺级隔离单元。 | 按应用-店铺对分别限流。不要 let 一个店铺的流量消耗另一个店铺的队列。 |
| App ID x 端点或资源 | 应用级端点，或不适用店铺级授权的端点 | 某些端点可能在应用/资源级别而非按店铺进行管理。 | 除店铺级限制器外，还需维护端点级限制器。 |
| 端点平台保护 | 平台级流量高峰或服务压力期间的任何端点 | 平台可能暂时降低所有调用者的可用容量，与您应用的正常请求速率无关。 | 退避并重试。不要假设添加店铺会立即解决此情况。 |
| 滥用、安全或网络保护 | 异常突发、高并发、可疑模式或基础设施级控制 | 可能在正常应用-店铺配额模型之外应用额外控制，包括 IP 或流量模式保护。 | 平滑流量，降低并发，如果在非常低的请求量下仍持续限流，请联系技术支持。 |
| 未授权或未绑定的店铺 | 对未授权应用的店铺或无效店铺标识的请求 | 这通常是授权或请求验证问题，而非可用的店铺级配额。 | 先修复授权或店铺身份。不要将其视为容量问题。 |
实现提示：不要硬编码一个全局 QPS 阈值。按应用、店铺、端点和操作类型使用单独的限制器，然后动态适应限流响应。
# 4. 限流信号和响应处理
## 4.1 HTTP 状态码与业务码关系
限流可能通过 HTTP 层和响应体同时呈现：
| **信号** | **含义** | **如何处理** |
| --- | --- | --- |
| HTTP `429 Too Many Requests` | 传输层限流信号。 | 视为被限流。停止受影响限制器的新请求，使用退避重试。 |
| 业务码 `36009002` | OpenAPI 业务错误码，表示限流或请求频率控制。 | 即使您的 HTTP 客户端或 SDK 分别呈现 HTTP 状态码，也应视为被限流。 |
| HTTP `429` 且 body 码 `36009002` | 最明确的限流响应：传输层和业务层一致。 | 视为被限流。记录两个字段用于诊断。 |
如果出现 HTTP 状态码 `429` 或业务码 `36009002`，将响应作为限流事件处理。对于监控，记录 HTTP 状态码和业务码，因为 SDK、网关和日志可能以不同方式呈现它们。
## 4.2 429 与 503 的区别
区分 `429` 和 `503` 是构建健壮客户端的前提。
| **HTTP 状态码** | **根本原因** | **操作** |
| --- | --- | --- |
| `429 Too Many Requests` | 您的应用超出了当前隔离单元内动态分配的容量，或端点达到了平台级保护性限流。 | 停止发送受影响限制器的新请求。如果存在 `Retry-After` 则使用它重试，否则使用指数退避加随机抖动。绝不要立即高频重试。 |
| `503 Service Unavailable` | 不是速率限制。底层服务可能过载、暂时不可用或正在维护中。 | 短暂等待后重试。如果持续出现，检查开发者公告或联系技术支持以确认是否有已知事件正在进行。 |
# 5. 最佳实践
## 5.1 使用批量 API
平台为许多场景提供批处理端点。只要存在批处理端点，就不要循环调用单项端点。将 N 次调用合并为一个请求是保持在速率限制以下的最有效方式。
批处理端点通常按每个 HTTP 请求计为一次调用，而非按批中的每项计数，除非端点文档另有说明。
## 5.2 使用请求队列和限流
维护内部请求队列并以平滑、受控的速率发送。避免在同一秒内触发许多请求的突发。按 App ID、店铺、端点和操作类型分别应用限流。
## 5.3 仅获取所需内容
将 API 请求精简为业务实际所需的最少字段和数量。当增量同步、基于游标的分页或 changed-since 过滤器可用时，避免全表拉取。
## 5.4 缓存热数据
在您的端缓存低变更、高读取的数据，如商品主数据、店铺配置、类目映射和参考字典。这可以大幅减少不必要的 API 流量。
## 5.5 构建幂等写入和分级错误处理

* 使写入操作幂等，以便重试不会产生重复或脏数据。
* 区分 `429`、业务码 `36009002`、`503`、其他业务错误和网络错误。
* 对每类应用正确的响应，而不是对所有情况使用同一种重试策略。

## 5.6 使用指数退避、抖动和 Retry-After
当您收到 HTTP `429` 或业务码 `36009002` 时，使用指数退避加抖动重试。如果响应包含 `Retry-After` 头，将其作为最短等待时间遵守。
```Plain Text
wait = max(retry_after_seconds, min(base_delay * (2 ** retry_count) + random_jitter, cap))
```

关键参数：

* `Retry-After`：如果存在，可能是秒数或 HTTP 日期。使用它避免在平台要求之前重试。
* `base_delay`：当没有 `Retry-After` 头时从 1 秒开始。
* 指数增长：每次失败将等待时间翻倍，例如 1s -> 2s -> 4s -> 8s。
* `cap`：限制本地生成的退避时间，例如 60 秒。如果 `Retry-After` 更长，遵守它或触发告警，而不是提前重试。
* `random_jitter`：添加小的随机偏移，例如 0-500ms，防止多个实例同步重试造成新的流量尖峰。
* `max_retry_count`：设置最大重试次数，例如 5 次。超过后，发出告警或回退到降级路径。

Python 参考实现：
```Python
import random
import time
from datetime import datetime, timezone
from email.utils import parsedate_to_datetime
from typing import Optional

def parse_retry_after(value: Optional[str]) -> Optional[float]:
    # 如果没有 Retry-After 值，返回 None
    if not value:
        return None

    try:
        # 尝试将值解析为秒数
        return max(0.0, float(value))
    except ValueError:
        pass

    try:
        # 尝试将值解析为 HTTP 日期格式
        retry_at = parsedate_to_datetime(value)
        if retry_at.tzinfo is None:
            retry_at = retry_at.replace(tzinfo=timezone.utc)
        # 计算从现在到重试时间的秒数
        return max(0.0, (retry_at - datetime.now(timezone.utc)).total_seconds())
    except Exception:
        return None

def backoff_sleep(
    retry: int,
    retry_after: Optional[str] = None,
    base: float = 1.0,
    cap: float = 60.0,
) -> None:
    # 计算指数退避时间加上随机抖动
    generated_wait = min(base * (2 ** retry) + random.uniform(0, 0.5), cap)
    # 解析 Retry-After 头部
    header_wait = parse_retry_after(retry_after)
    # 取两者中的较大值
    wait = max(generated_wait, header_wait) if header_wait is not None else generated_wait
    time.sleep(wait)
```

# 6. 常见问题
## Q1：我如何知道我的应用获得了多少 QPS 配额？
配额是动态计算的。平台不为所有端点暴露固定配额查询 API。如果端点参考文档发布了明确的限制，请优先使用。否则，使用第 2.2 节中的容量规划基线作为保守起点，然后通过逐步增加和限流指标测量您的稳定速率。
## Q2：我的业务增长很快。如何增加 QPS 配额？
动态分配机制的核心理念是总容量通常随授权店铺规模增长。最直接和推荐的路径是扩展您的店铺授权规模。
但是，不要假设每增加一个店铺就会为每个端点增加相同的固定 QPS。关系可能是非线性的、按端点加权的、阶梯式的，并受平台负载影响。授权变更也可能有传播延迟。对于高峰事件，请逐步增加。
## Q3：我很少发送请求。为什么仍然偶尔看到 429 或 36009002？
常见原因包括：

1. **亚秒级突发**：即使平均 QPS 很低，同一秒内的多个请求也可能触发限流。使用请求队列平滑发送。
2. **平台级保护性限流**：当端点的平台级负载达到保护阈值时，平台可能暂时降低所有调用者的容量。这与您应用的正常请求速率无关。
3. **同一隔离单元内的并发竞争**：多个应用实例可能在毫秒级窗口内叠加请求，即使每个实例单独看起来是安全的。
4. **端点级约束**：某些端点可能有比整体应用-店铺容量更严格的资源级限制。

处理方式相同：降低并发，退避，遵守 `Retry-After`（如果存在），并使用抖动重试。
## Q4：批量端点和单项端点的 QPS 如何计算？
批处理端点通常按每个 HTTP 请求计为一次调用，而非按批中的每项计数。只要批处理端点可用，优先使用它。请参考每个端点的文档了解其确切的计数规则。
## Q5：我是否应该重试每个 429 或 36009002 响应？
仅在退避后重试。立即高频重试可能加剧限流并延长限制。对于写入 API，仅在操作是幂等的或受幂等机制保护时才重试。
